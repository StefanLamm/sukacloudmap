# 配送费用优化核查

## 问题与计费口径

本轮针对 2026-11-13「test1」V1 的淮安 5 店拆车问题。冻结输入共 225 店、4378 件，与用户提供的需求表逐编号、逐件数一致。淮安 5 店合计 117 件，该仓可用车辆容量均为 400 件。

V1 保存的两条淮安线路合计 290.59 元。最终验证记录显示其中一条线路使用了 `unused_car_split` 修复，说明拆车发生在道路复核阶段。原失败线路的完整顺序及全部失败回执没有保存在该版本中，因此不能断言某一具体到店时间就是当时的原因。

在同一冻结道路图上，两条原线路仍合计 290.59 元。独立枚举这 5 店的所有非空子集及顺序，并比较三辆物理车辆和共配组合，得到 269.10 元的一车方案：117 件、46.396 公里、09:00 发车、13:27:58 卸货结束，减少 21.49 元（7.40%）。该结论仅针对这 5 店、给定车辆、报价与固定道路指标，不是 225 店全局最优或实时货车执行证明。

数据库中同时保留用户人工合并后的 V2。V2 的淮安线路也是 269.10 元，但全日费用高于 V1，因此全日比较不能只取 V2 作为较高基准。所有已有版本保持不变。

## 改进方法

- 大日中的小型相容任务组：按同仓、完整报价参数分组，最多 7 店时枚举顺序与子集。原多起点搜索和合池完成后，才使用选线阶段剩余预算补强一次，最多 3 秒或总预算的 5%，按原调度为最终道路验证预留 17%（另记录初始化与完整校验开销）。先比较完整覆盖，再比较部分专车与共配组合；仅沿已测有向路段枚举，提前排除缺边和超载前缀，接受前仍由完整评估器核实。
- 大报价组内的同城候选：若完整相容组超过 7 店，再根据明确的省、市资料生成 2～7 店子组。test1 的淮安 5 店属于含淮安、宿迁、徐州的 16 店报价组，这一步补足了仅看完整组规模的遗漏。城市仅用于候选生成，不限制跨城配送；不把缺失城市资料合并成一组，不重复使用同一物理车辆，也不强制使用专车。
- 道路变化后的修复：最多 8 店的小线路比较完整重排，不再只依赖一次区间反转。旧缓存缺边或旧时长冲突不能直接淘汰重排；缺失连接受本轮桥边数和时间预算限制，统一使用本轮采集回执核算。
- 终局合车：对兼容的两条小线路重新排顺序，并重新核算完整方案。只有实际总费用、里程、车辆数按既定顺序更优时才采用，保留多车更便宜的情况。
- 搜索保护：预算到期保留已验证方案；取消请求仍生效；失败道路在同批次不重复请求。先让所有受影响线路恢复可行，再进一步降低费用，避免第一条线路耗尽修复时间。小组补强不增加道路请求；修复阶段给其他受影响线路保留桥边预算，后优化不能占用其他线路的物理车辆。
- 道路调用额度保护：真实普通驾车任务设置有限总额度时，按有报价且可由同仓可用车辆承运的任务数，为最终复核预留每个任务一次方向调用。所有探索阶段共用余下额度，复核前恢复原总上限；异常和取消也恢复。总额度小于任务数时，探索仅使用已知道路。此预留不覆盖所有 HTTP 重试和新增桥路，不提高用户设置的总上限，也不把搜索回执冒充最终新鲜回执。

此前已有 ALNS、混合搜索、整车组合选择及跨轮候选池，本轮沿用其费用优先目标。方法复核参考 [Vidal 的 SWAP* 原论文](https://arxiv.org/abs/2012.10384)、[带时窗的 HGS 实现说明](https://wouterkool.github.io/publication/hgs-vrptw/) 和 [OR-Tools 的邻域算子定义](https://github.com/google/or-tools/blob/stable/ortools/constraint_solver/routing_parameters.proto)。本轮针对本应用的道路复核及报价约束补充局部精确搜索，没有将通用 CVRP 的距离目标或最少车辆目标直接替换本应用费用模型。
