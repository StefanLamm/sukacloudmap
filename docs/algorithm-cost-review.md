# 配送费用优化核查

前半部分保留此前 `6a4de71` 的 test1 优化及验收记录；其中“原算法”指当时的 `f207376`。后续冷启动优化以 `6a4de71` 为新基准，另列对照，避免混用两轮实验。

## 问题与计费口径

本轮针对 2026-11-13「test1」V1 的淮安 5 店拆车问题。冻结输入共 225 店、4378 件，与用户提供的需求表逐编号、逐件数一致。淮安 5 店合计 117 件，该仓可用车辆容量均为 400 件。

V1 保存的两条淮安线路合计 290.59 元。最终验证记录显示其中一条线路使用了 `unused_car_split` 修复，说明拆车发生在道路复核阶段。原失败线路的完整顺序及全部失败回执没有保存在该版本中，因此不能断言某一具体到店时间就是当时的原因。

在同一冻结道路图上，两条原线路仍合计 290.59 元。独立枚举这 5 店的所有非空子集及顺序，并比较三辆物理车辆和共配组合，得到 269.10 元的一车方案：117 件、46.396 公里、09:00 发车、13:27:58 卸货结束，减少 21.49 元（7.40%）。该结论仅针对这 5 店、给定车辆、报价与固定道路指标，不是 225 店全局最优或实时货车执行证明。

数据库中同时保留用户人工合并后的 V2。V2 的淮安线路也是 269.10 元，但全日费用高于 V1，因此全日比较不能只取 V2 作为较高基准。所有已有版本保持不变。

## 改进方法

- 大日中的小型相容任务组：按同仓、完整报价参数分组，最多 7 店时枚举顺序与子集。原多起点搜索和合池完成后，才使用选线阶段剩余预算补强一次，最多 3 秒或总预算的 5%，按原调度为最终道路验证预留 17%（另记录初始化与完整校验开销）。先比较完整覆盖，再比较部分专车与共配组合；仅沿已测有向路段枚举，提前排除缺边和超载前缀，接受前仍由完整评估器核实。
- 大报价组内的同城候选：若完整相容组超过 7 店，再根据明确的省、市资料生成 2～7 店子组。test1 的淮安 5 店属于含淮安、宿迁、徐州的 16 店报价组，这一步补足了仅看完整组规模的遗漏。城市仅用于候选生成，不限制跨城配送；不把缺失城市资料合并成一组，不重复使用同一物理车辆，也不强制使用专车。
- 道路变化后的修复：最多 8 店的小线路比较完整重排，不再只依赖一次区间反转。旧缓存缺边或旧时长冲突不能直接淘汰重排；缺失连接受本轮桥边数和时间预算限制，统一使用本轮采集回执核算。
- 终局合车：对兼容的两条小线路重新排顺序，并重新核算完整方案。只有实际总费用、里程、车辆数按既定顺序更优时才采用，保留多车更便宜的情况。
- 搜索保护：预算到期保留已验证方案；取消请求仍生效；失败道路在同批次不重复请求。先让所有受影响线路恢复可行，再进一步降低费用，避免第一条线路耗尽修复时间。小组补强不增加道路请求；修复阶段给其他受影响线路保留桥边预算，后优化不能占用其他线路的物理车辆。
- 道路调用额度保护：真实普通驾车任务设置有限总额度时，按有报价且可由同仓可用车辆承运的任务数，为最终复核预留每个任务一次方向调用。所有探索阶段共用余下额度，复核前恢复原总上限；异常和取消也恢复。总额度小于任务数时，探索仅使用已知道路。此预留不覆盖所有 HTTP 重试和新增桥路，不提高用户设置的总上限，也不把搜索回执冒充最终新鲜回执。

此前已有 ALNS、混合搜索、整车组合选择及跨轮候选池，本轮沿用其费用优先目标。方法复核参考 [Vidal 的 SWAP* 原论文](https://arxiv.org/abs/2012.10384)、[带时窗的 HGS 实现说明](https://wouterkool.github.io/publication/hgs-vrptw/) 和 [OR-Tools 的邻域算子定义](https://github.com/google/or-tools/blob/stable/ortools/constraint_solver/routing_parameters.proto)。本轮针对本应用的道路复核及报价约束补充局部精确搜索，没有将通用 CVRP 的距离目标或最少车辆目标直接替换本应用费用模型。

## 后续冷启动优化：以 6a4de71 为基准

本轮从当前需求构造可行起点，同时给一轮原生搜索保留独立首解，再按实际整单费用选择专车与共配组合。29 日、每版 30 秒的离线对照为 **318656.19→316050.81 元，降低 2605.38 元（约 0.82%）**；14 日降低、8 日相同、7 日升高。仍有负例，不能声称逐日或每个 seed 都不增费。

基线为开始开发时的 `test` 提交 `6a4de71`；最终算法源码清单摘要为 `b754de092c50d50d491516f47ac98c62ab52498db745cd2e6ed96ba6a28c648e`。摘要不是发布标签；上文 test1 V5 是历史保存方案且从已有方案继续优化，不是本轮真冷启动。开发中的中间版本和小范围筛选均另存本机，不混入本节最终费用。

### 改动及预算

- 先由本次输入和已测有向道路构造完整起点，再运行原 HYBRID／GLS／ALNS 等组合。起点不读取旧完整方案；有必送任务导致全共配基线不完整时，沿用原主搜索。已有更低且合法的外部起点继续保留，诊断分别记录输入起点、内部构造和实际采纳，不把被拒绝或不完整的低费用当作当前完整最优。
- 真冷启动的第 2 轮（首次 GLS） 不传入当前起点，让首个 native slice 独立构造首解，避免所有轮次都从同一车辆组合继续；后续 slice 找到解后仍可沿该 assignment 搜索。其他轮次及显式提供外部方案的 warm 路径保持原规则。独立轮更贵或不完整时，Deep 继续保留此前较低价完整解；诊断记录每轮初始化来源，不增加轮次或预算。
- 长线路允许暂时不划算的前缀继续生长，比较空闲车承接共配、同仓且完整报价相容的跨城线路。城市只是候选焦点，不限制跨城；组外线路、必送任务和物理车不复用等保护保留。
- 城市近仓入口与高共配入口并用，焦点链／全局链按 3:1 交织；全局种子轮转高共配、远、近、早窗。默认上限仍为 36 条启动链、40 店／链及 14000 次评估。
- 增加头部、中间、尾部插入。按已测正向桥边的增量和共配机会费筛选三个位置，再核算完整线路的实际费用、容量与全部时窗。反向道路不能替代正向桥；排序值不作金额证明，短名单不是穷举。
- 原主搜索的身份／顺序观察路径仍轻量保留前 10000 条，多轮完整分配独立保护。起点候选另有独立入口。未采用开发中的缓冲与费用堆排序模块，未在逐候选主热路径增加这些工作。
- 统一选线先按仓库、可用性及容量筛物理车，等价车共享紧凑指标计算；选中后仍用实际物理车重建证据。新增的全可共配候选若整线专车不低于逐店共配，可从普通池移除；必送和保护的完整分配保留。按完整覆盖、整数分费用、里程、车辆数依次择优，不以少车替代低费。
- 后处理优化固定门店集合和物理车的顺序，比较整线／部分门店转共配及兼容小线合并。长线构造和固定集合顺序优化要求实际整单费用严格下降；删点转共配与合线沿原整单排序，费用不增，同价再比较里程和车辆数。post 内顺序优化／清理提前结束时，把当前剩余 post 时间的 75% 交给原小组精确生成，余量供组合，避免空置预算造成原有小组候选漏生成。

构造起点的真实时间计入原 64% 主搜索额度，不外加计算时间；原生搜索轮次时间相应缩短。宏不再在主搜索后重复执行，统一选线可使用验证前剩余的原有额度，整体仍受 83% 调度上限约束。起点最多 3 秒或总预算的 6%，post 最多 3 秒或总预算的 5%；它们是可取消的软上限，单次完整证明或 native 操作可能越过局部切片。道路调用预留及最终新鲜回执要求保留，缺失方向不补直线估价。有限已测候选池最优不代表所有可能路线的全局最优。
