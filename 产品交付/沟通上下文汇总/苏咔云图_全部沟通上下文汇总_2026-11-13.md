## 一、产品最初要解决的问题

用户每天导入“哪家门店下货、下多少件货”，系统根据门店位置、所属出货仓、货量、车辆容量和承运报价，决定：

1. 哪些门店由专车配送，使用哪辆车。
2. 每辆专车按什么顺序配送，路线怎么走。
3. 哪些门店使用共配拼车。
4. 完成全部配送需要支出多少费用。
5. 哪些任务无法分配，具体原因是什么。

**核心目标：在满足配送硬性条件的前提下，以最低支出完成所有门店的货物配送。**

装载率、里程和车辆数都是帮助降低费用的因素。不能只追求少用车或高装载率：如果多用几辆专车能明显减少共配费用、降低总支出，应采用总支出更低的方案。不能通过漏掉门店、不计某项费用或隐藏不合规线路来获得低价。

最初用户要求通过逐题澄清完善逻辑，产出产品经理工作方案，包括目标、步骤、各阶段开发与测试提示词、验收标准及方案文件；之后又明确要求按交接方案实际编写应用代码、持续完成开发、测试并发布网站。

## 二、已确认的产品与业务基线

| 项目 | 最终确认规则 |
| --- | --- |
| 产品形态 | 内部人员使用的电脑端网页应用，有账号密码登录 |
| 数据空间 | 内部账号共用业务资料；管理员管理账号；不做公众注册或多租户计费 |
| 规模基准 | 最初讨论2仓，后明确调整为4仓、800店、24000件、50辆专车；这是规模验收基准，不是写死的数量限制 |
| 日常需求输入 | 门店及下货件数，货物规格一致，以“件”为业务计量单位 |
| 车辆装载 | 按最大可装件数判断；件数不等于重量，不从件数随意推算实际载重 |
| 单店运输 | 同一出货仓发往同一门店的当天货物整批安排，不拆成多车或专车与共配两部分 |
| 出货仓 | 门店可以选择和修改出货仓；车辆也有指定出发仓；按冻结的业务安排规划，不擅自换仓或跨仓提货 |
| 车辆可用性 | 只使用已录入且当天可用的实际车辆，不得在不同报价组中重复使用同一辆物理车辆 |
| 车辆趟次 | 用户明确一辆车一天只能跑一趟；需求分组支持独立规划，不应将分组隔离误解为额外生成真实运力 |
| 返仓 | 不计算返仓里程、时间和费用，路线从仓库开始、到最后一家门店结束 |
| 续航 | 用户明确取消续航字段和续航约束 |
| 车辆归属 | 不区分自有或外部车辆，按维护的承运报价核算 |
| 车型与报价 | 同一报价下不同装载能力车辆同价；容量用于可行性，不擅自乘车型倍率 |
| 跨城合线 | 同仓且完整计费规则、价格兼容时可跨城市配送；不能仅因城市不同拆线 |
| 共配 | 共配就是拼车，逐门店按件单价收费；单价按门店维护，不强制按城市统一 |
| 共配时效 | 用户明确共配不会迟到，不安排或校验共配到店、营业和卸货时间 |
| 专车发车 | 仓库设置当天最早发车时间，专车不能早于该时间出发 |
| 收货时间 | 营业时间内均可收货，以营业时间为基础，不强加独立收货时间维护；保留实际已有的特殊当日限制能力 |
| 最晚送达 | 指车辆到店时间，不指完成卸货时间；后续明确默认参考门店营业结束时间 |
| 卸货 | 每家门店可设置卸货时长，计入后续门店时序 |
| 提前到店 | 可以等到开门；等待计入后续路线时间 |
| 跨日营业 | 支持次日闭店，使用完整日期时间核算 |
| 关门边界 | 允许关门前到店、关门后卸完；不能把卸货结束时间误当成最晚到店时间 |
| 历史 | 每次规划或核算追加版本，保留当时需求、报价、道路及输入快照，后续修改资料不改旧版本 |
| 最优性 | 保存限时内找到并通过完整校验的最低费用可行方案；有限候选池最优不等于所有可能线路的全局最优 |

## 六、报价方案与所有附加费口径

### 6.1 基础公式

按公里计费：

```text
线路专车费 = 各段真实道路米数合计 ÷ 1000 × 每公里单价
```

起送加串店：

```text
线路专车费 = 起送价 + max(实际配送门店数 - 起送价包含门店数, 0) × 串店费
```

共配：

```text
门店共配费 = 该店配送件数 × 该店共配每件单价
总支出 = 所有专车线路费 + 所有门店共配费
```

起送价包含几家门店可在每份报价中单独设置，不能写死为一家。缺少某种运输方式的报价时，不以0元代替。0元与空值含义不同。实际金额按十进制、到分舍入，不能把搜索权重当成真实费用。

### 6.2 特殊地区附加费的需求演变

用户先要求两种新增模式：

- 按公里计费＋特殊城市/区县附加费。
- 起送加串店＋特殊城市/区县附加费。

随后补充：省→市→区县逐级选择，地区可多选；最终需要明确区分三种附加费粒度：

| 粒度 | 含义 |
| --- | --- |
| 整条线路一次 | 线路送达任一命中地区，整线加一次费用 |
| 每个送达区县一次 | 按实际送达且命中的不同区县分别计费，同区县多店只计一次 |
| 每家命中门店 | 每个命中特殊地区的门店分别加费，同区县有多家店则按店累计 |

同店同时命中城市和区县范围时避免重复计费；不同城市的同名区县不能误合并。地区资料不足以判断时提示费用待核对，不能默认无附加费。旧报价和历史方案保持旧语义，不悄悄改写。

### 6.3 报价兼容与跨城

同仓且完整计费模式、单价、起送包含店数、串店费、特殊地区集合及收费粒度等参数兼容时，可合并专车线路。不能只比较报价名称或城市，也不能把不兼容计费强行套成一条线路。

## 七、每日需求分组、输入快照和历史

用户要求：每天可以新建多个需求分组，先选择分组，再在组内创建或导入需求；门店与报价校验、方案规划与调整都必须选择分组后进行。

- 分组隔离保存需求、来源数据、当日限制、仓车安排、输入快照、规划任务和方案历史。
- 删除需求分组时，组内上述业务数据同步级联删除；其他分组和基础资料保留。
- 删除后仍运行的任务不能重新把已删除组的数据写回来。
- 历史业务按配送日迁入“历史需求”等分组时，原账号密码、快照和方案内容保留。
- 同日版本号可连续编号，各分组当前方案与历史列表分别维护。
- 新分组不自动继承其他分组的旧方案或低价结果。

导入要求：

1. 上传文件后选择工作表、表头及列匹配。
2. 按当前配送日期过滤月表，不把其他日期混入当日。
3. 匹配门店采用稳定编号等可信信息，遇到重名或歧义不自动猜测。
4. 预览行错误、重复汇总及替换前后差异。
5. 重复上传按当前组替换，避免件数翻倍；无目标日期的数据不能意外清空已有需求。
6. 确认后形成可追溯输入快照；基础资料或需求改变后重新冻结，历史快照不改写。

保存任务结果前再次核对创建者有效性、当前输入和方案版本。出现输入变化、账号停用、版本冲突或组已删除等情况，不能覆盖当前业务或追加误导性“已保存”方案。

## 八、自动规划与人工调整

### 8.1 日常操作

```text
选择配送日期 → 新建/选择需求分组 → 创建或导入件数
→ 核对仓库、车辆、报价及门店时间 → 冻结输入
→ 方案规划与调整 → 开始规划
→ 查看费用、专车、共配、异常、地图及历史版本
```

默认最晚到店取门店闭店时间。普通驾车方案的预计时间属于参考，不能当作已验证的未来货车执行时刻。

### 8.2 人工调整的最终要求

- 可直接改配送方式、指定实际车辆、调整配送顺序。
- 保留具体车辆选项，并增加“专车（自动分车排线）”：根据货量、线路、容量和可用车辆自动安排车辆及顺序。
- 调整后选择“是否优化线路”。
- 不优化：严格按人工给定车辆及顺序核算，不悄悄重排。
- 优化：在保留相应人工约束下以最低费用为目标排线；不能把只追求最短距离当成最低费用。
- 点击“开始核算”才生成新的线路报价和版本。
- 核算后显示旧费用、最新费用、专车与共配分项及增减额。
- 未保存的人工选择与已保存结果区分；费用、轨迹属于上一次结果时应说明。
- 失败或并发版本冲突保留人工选择，不能静默覆盖。
- 页面离开确认改用应用内不阻塞弹窗，避免原生确认框阻碍浏览器操作。

### 9.3 最终调用规则

- 用户后来明确将高德算路单任务总调用上限从10次改为无限制，先前10次授权不再作为普通驾车任务总次数上限。

## 十二、算法改造的完整沟通背景

用户在test2分组发现：现有方案少用专车，却没有最低费用；增加专车可能进一步降低总支出。因此先要求比较更多专车/共配比例，再提出全面调整线路逻辑，并允许网上学习更先进算法。

用户提出的参考方向：提高专车装载率、合理规划并尽量缩短每条专车里程、对同一需求计算大量专车/共配组合，找出最低总支出。曾要求在10小时内测试不同算法；后续记录为分层长时间算法对照，不能把一次5分钟日常任务等同于全部历史长测。

已研究及应用的方法包括多起点候选、OR-Tools引导局部搜索、模拟退火/禁忌等策略、自适应大邻域搜索、跨轮线路池和整数联合选择。实际选择以真实报价核算费用；覆盖、容量、同仓、时序和车辆物理占用通过独立检查器复核。

0.14历史正式对照共103轮，使用冻结输入和26883条实测道路参考，60秒初筛、300秒复筛、优胜方法1800秒长测。各阶段预算和输入变化分别记录，不能声称所有方法总预算完全相同。最长单次1800秒实测不等于已做24000秒持续稳定性验收。

曾有候选池报价23278.47元，但最新道路耗时导致部分门店迟到，未把该价格当作已保存可行方案。路况改变时必须重新报价和校验，不能只保留数字更低的旧结果。

## 十三、0.15日常深度选优已经如何集成

用户追问新算法是否已经用于以后所有新需求分组，随后明确要求：完整多轮多种子、跨轮线路汇总、联合选优、高德校验接入日常“开始规划”，完成测试并发布。

**用户已确认日常默认计算5分钟，即300秒；页面可调到24000秒。高德道路请求与限流排队另计，并有任务等待边界、支持取消。**

当前自动工作链：

```text
冻结当前分组输入
→ 多轮、多种子、多策略搜索
→ 汇总各轮线路与完整配送方案
→ 以当前货量、报价、车辆和时间条件重新核算候选
→ CP-SAT联合选择专车线路、共配及实际车辆
→ 自动采集并固定本轮高德实际道路回执
→ 发现时窗冲突后进行重排、共配、车辆等修复比较
→ 只为新连接补采道路，避免已采道路重复刷新漂移
→ 固定真实道路后再次联合选优
→ 独立复核覆盖、费用、约束和逐段证据
→ 核对当前输入与方案版本，追加保存最低已发现可行方案
```

技术与行为细节：

- 一个规划任务内串行多轮，多个可复现种子，不是多个任务重复写同一方案。
- 普通常规候选最多保留10000条并记录截断情况；各轮完整分配方案另行保留。
- 以整数分核算，有限候选池先最小总费用；条件满足时固定费用后再最小里程、再最少物理车辆。
- 每票恰好分配一次，不拆票；同一实际车辆不能在多条候选线上重复占用。
- 同分组、同快照的旧方案可以作为当前任务完整候选；新分组不继承其他组方案。
- 搜索阶段历史实路可作为参考，但最终普通驾车实时标签必须有本轮真实回执。
- 已取得的本轮同向同坐标道路在任务内固定，不反复刷新导致路况不断变化、校验永远追不上。
- 后端在写入前再次独立验证道路坐标、采集时间、米数、秒数和证据哈希；不允许伪造本轮来源。
- 未找到完整合法方案时明确失败并保留输入，不将未分配、费用不完整结果作为正常成功方案。
- 取消、离线参考、固定道路样例、全共配、实时普通驾车等状态清楚区分。
- 前端展示阶段、轮次、种子、候选数、当前参考最低费用；只有道路复核后才能说明最终报价。
- 普通驾车方案仍不能点击成“货车已确认可执行”。
